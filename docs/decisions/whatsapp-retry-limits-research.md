# Spike: bounded WhatsApp retries and fresh-first claims — decision notes

**Status:** research; maintainer answers recorded 2026-10-09 (see [Maintainer decisions](#maintainer-decisions-2026-10-09)), which supersede the TL;DR where they differ. Specified in [#79](https://github.com/fillthemat/fillthemat/issues/79); not implemented.
**Date:** 2026-10-09
**Scope:** [issue #68](https://github.com/fillthemat/fillthemat/issues/68), before the Phase 6 pilot. Code checked at `0dcc40f`; vendor documentation fetched on the date above. No code, database, env, or scheduler changes were made.

---

## TL;DR recommendation

1. **Stop permanent failures immediately; allow five total executions for transient/unknown failures** (initial execution + four retries). Keep the existing exponential backoff; stop free-form deliveries earlier when their real customer-service window closes. Apply the same classification to synchronous sends and failed status callbacks (§1–2).
2. **Add `dead` to both WhatsApp state enums.** Keep `failed` meaning retryable. Retain the row, error and attempt count; exclude `dead` from claims, recovery and automatic resurrection. Log the terminal transition once and monitor terminal counts using the pilot's existing logs/table workflow; no automatic prospect WhatsApp or School Owner email in this issue (§3).
3. **Order due claims by `attempts ASC, created_at ASC, id ASC`.** This puts first executions ahead of retries, preserves deterministic oldest-first ties, and does not change the due-time gate or `SKIP LOCKED` transaction. Keep current due indexes initially; measure before adding an order-oriented partial index (§4).
4. **Close bypasses, not just `failJob`.** Count started executions durably (including accepted sends), do not count single-flight deferrals, bound stale-claim recovery, and classify failed callbacks without counting the same send twice (§2).
5. **Quarantine existing poison rows, then fix test cleanup.** Do not reset the shared Supabase stack or delete jobs by a broad `199…` prefix. Correct the window-error reference to **`131047`**, and make explicit that generic closed-window replies have no template fallback today (§5–6).

These are proposed policy choices, not vendor-prescribed limits. The grounding and remaining maintainer choices follow.

## Grounding: what exists today

- Claims are **Drizzle transactions in TypeScript**, not Postgres stored functions: select due `pending|failed`, lock with `FOR UPDATE SKIP LOCKED`, limit 10 jobs / 25 deliveries, update those IDs to `claimed`, return the original selected rows. Neither select has `ORDER BY` (`src/lib/whatsapp/jobs.ts:37–73`; `src/lib/whatsapp/deliveries.ts:122–161`). Worker processing is sequential: one jobs batch, then one deliveries batch, with inline sends during job processing (`src/lib/whatsapp/worker.ts:143–164,415–450`). The two tables have separate quotas: poison deliveries do not literally consume the ten job slots, but consume worker time; poison jobs can displace new inbound jobs.
- Migrations are **Drizzle-owned in `drizzle/`**, not `supabase/migrations/` (`drizzle.config.ts:3–10`). Job enum: `pending|claimed|done|failed`; delivery enum: `pending|claimed|sent|delivered|read|failed` (`src/db/schema.ts:46–56`; `drizzle/0005_groovy_raider.sql:1–18`; `drizzle/0001_silky_fantastic_four.sql:1–24`). No terminal failure state exists.
- Both tables have `attempts DEFAULT 0`, non-null `next_attempt_at DEFAULT now()`, claim fields, `last_error`, timestamps, and a B-tree `(state,next_attempt_at)` due index. Jobs have unique `dedupe_key`; deliveries have unique `provider_idempotency_key`. Deleting a School nulls job `school_id` but cascades deliveries (`src/db/schema.ts:592–672`; `drizzle/0005_groovy_raider.sql:22–23`; `drizzle/0001_silky_fantastic_four.sql:30–33`). No failure code/category column exists.
- **`attempts` currently counts recorded synchronous failures, not executions.** Failure increments it and sets 1, 2, 4, 8, … minutes, capped at 60, without any limit. Success does not increment it; failed status callbacks and stale-claim recovery do not increment it either (`src/lib/whatsapp/jobs.ts:6–9,92–108,132–152`; `src/lib/whatsapp/deliveries.ts:12–15,179–279,344–362,386–406`). Thus changing only the synchronous failure writers misses repeat accepted-send → failed-callback cycles and repeated crashes.
- The inbound route schedules `after()` only for inbound messages; status-only callbacks do not wake the worker. It logs persistence failures but still returns 200. The WhatsApp cron authenticates and returns worker counters, **without writing `cron_runs`** (`src/app/api/webhooks/whatsapp/route.ts:79–112`; `src/app/api/cron/whatsapp/route.ts:5–10`). Daily wake is 05:00 UTC (`vercel.ts:18–23`). Backoff is an **earliest eligibility time**, not a timer.

## 1. Failure inventory and classification

**Permanent** below means “do not retry this unchanged row automatically,” not “the condition can never be repaired.” Approval, credentials and template approval can change; deliberate replay after repair is different from indefinite polling. **Transient** means bounded retry, not guaranteed recovery. SDK/database exceptions are open-ended, so inventory their catch boundaries and explicitly named errors rather than inventing a finite list of possible library messages.

## 2. Decision 1 — retry budget and execution semantics

| Option | Tradeoff |
| --- | --- |
| A. Five executions for everything | Smallest cap-only change, but wastes five slots on unknown numbers/closed windows, and ignores provider “do not retry” guidance. |
| **B. Permanent stop + five total executions for transient/unknown (recommended)** | Small classifier and shared failure transition; bounds work without premature two-attempt exhaustion. Preserves more unknown failures than an allowlist-only policy. |
| C. Retry only an explicit transient allowlist; eight executions / larger TTL | Strong fail-closed behavior but drops new provider failure types immediately; more budget cannot fix slow wake-ups and risks stale replies. |

**Why five:** existing backoff gives retry eligibility at 1, 2, 4 and 8 minutes after successive failures (15 minutes cumulative if workers wake on time; derived from `src/lib/whatsapp/jobs.ts:6–9`). This is a tunable pilot policy, not a promise to retry within 15 minutes: idle traffic + daily cron can stretch template retries across days (`vercel.ts:18–23`; `docs/decisions/whatsapp-cron-after.md:249–263,504–507`). Do not add sub-daily cron silently; the accepted decision defers that (`docs/whatsapp-plan.md:331–333`).

**Make the cap real:**

- Prefer **durable started-execution counts**, rather than continuing the failure-only meaning of `attempts`. Increment once immediately before real job work / outbound request, persist before side effects, and use that same count when deciding retry/exhaustion. Successful accepted sends then have nonzero attempts; callback failure schedules against that execution, **without an extra increment**. At count five, a failure or stale recovery goes `dead`; a fifth successful send may still advance to delivered/read. Preflight permanent rejection can stop without a network call.
- For jobs, check dedupe and acquire conversation single-flight before reserving a real execution; a busy conversation remains a **deferral**, not an error consuming the budget. Unknown-number rejection is terminal regardless of its prior count. Single-flight deferral does not magically become `dead` after five claims (`src/lib/whatsapp/worker.ts:346–369`).
- Stale recovery must preserve nonzero execution counts and exhaust at the cap; unfinished claims that never began real work can be requeued without consuming a send. Add claim-owner/state guards to reservation/finalization so an old worker cannot overwrite a recovered claim. Today final writes use only row ID (`src/lib/whatsapp/jobs.ts:76–124`; `src/lib/whatsapp/deliveries.ts:179–278`). A five-minute recovery threshold is not fencing.
- Failed callback processing must be idempotent by provider attempt and timestamp, must not double-schedule synchronous + async reports, and must not reopen `dead`. Existing timestamp guards help but missing callback timestamps use `new Date()`; delivery state updates have no atomic expected-state condition (`src/lib/whatsapp/deliveries.ts:335–377`). Preserve positive delivery/read evidence; current failure path protects only `read`. Later success for the **same accepted attempt** may reconcile to delivered/read, never pending/failed. Retried sends overwrite the only `provider_id`; full provider-attempt history is a separate extension if required (`src/lib/whatsapp/deliveries.ts:254–264,328–332`).
- Centralize one retry/terminal policy used by jobs, delivery preflights, send failures, callbacks and recovery. Keep machine reason (`unknown_phone_number`, provider code, etc.) separate from human summary and terminal cause (`permanent` / `attempts_exhausted`); never replace useful provider error with only “max retries.” A structured `last_error_code` / terminal-reason field is preferable to repeatedly parsing the two incompatible error strings noted in §1.

**External timing/idempotency constraints:** the customer-service window starts/resets when the **user messages**, not when the worker processes it; only approved templates are allowed outside it ([Meta service messages][meta-messages]). The current parser discards inbound timestamp, and worker/confirmation expiry is processing time +24h (`src/lib/whatsapp/parse.ts:1–8,92–98`; `src/lib/whatsapp/worker.ts:103,149,216`; `src/lib/whatsapp/booking.ts:92–93`). Delayed job retries can therefore manufacture a false fresh window. Implementation should carry the verified inbound timestamp/use real last inbound, or explicitly track this as a pre-pilot correctness follow-up; do not extend expiry on every retry.

An accepted Graph response is **not delivery**; Meta reports status by webhook and may itself retry delivery up to message TTL (currently 30 days except authentication templates' 10 minutes). Do not resend `sent` just because no callback has arrived ([Meta service messages][meta-messages]). Our unique key only dedupes **local inserts**; it is not sent as a Graph idempotency header (`src/lib/whatsapp/deliveries.ts:94–119`; `src/lib/whatsapp/client.ts:40–48`). Network ambiguity / send-success-DB-failure / crashed sender can duplicate sends: bounded retries reduce exposure but do not establish exactly-once delivery. For booking templates, consider a usefulness deadline (e.g. booking start) separately from the five-attempt budget; do not accidentally send obsolete confirmations days later (`src/lib/whatsapp/booking.ts:183–196`).

## 3. Decision 2 — terminal state and who is told

| Option | Tradeoff |
| --- | --- |
| A. Make `failed` terminal; put retries back into `pending` | Avoids enum addition, but changes all existing `failed` meanings, backfill/monitoring expectations, and combines fresh work with retry state. |
| **B. Add `dead`; retain retryable `failed` (recommended)** | Additive, explicit dead-letter state; no new table/queue. Existing claim predicates naturally exclude it. Requires enum migration + schema/types + all-path guards. |
| C. Add `retryable=false` / `terminal_at` while retaining `failed` | More metadata, but every claim/recovery/status path needs the right boolean predicate; easier to accidentally resurrect work than a distinct state. |

Retain payload/error/count/dedupe keys; clear active claim fields on release/terminal transition. `next_attempt_at` is currently non-null, so leave its historical value on `dead` (ignored), rather than inventing a far-future timestamp or broad nullability change (`src/db/schema.ts:613–620,655–660`). Do not call rejected jobs `done`, which today also represents successful processing. Add `dead`/`deferred` counters so failure vs exhaustion vs lock deferral is visible; current worker counters cannot distinguish them (`src/lib/whatsapp/worker.ts:366–369,415–427`; `src/lib/whatsapp/deliveries.ts:282–310`).

### Notification options

1. **Logs + operator table query (recommended for pilot):** one structured terminal event with row ID, school ID when known, reason/code, attempts and run ID; aggregate retryable/terminal counts + oldest due age. No message body, phone, raw wamid or unsanitized SDK/DB error in the event. This reuses the rollout's explicit “Vercel logs + query on failed counts,” expanding to `dead` (`docs/whatsapp-phase6-kickoff.md:191–203,225–227`). It is visibility, **not an automatic notification**: assign an operator to check it.
2. Rate-limited **operator email / log alert** for credential outages, unknown-number spikes and exhausted booking confirmations: better detection, but no existing WhatsApp alert recipient/job kind exists. It needs recipient, dedupe, batching and recursion policy; follow-up if manual pilot checks are insufficient.
3. **School Owner email per failed delivery:** existing notification email and owner booking/lead mail are available, but per-row delivery alerts are a new email kind and can produce their own retry storm. Do not notify prospects via the broken WhatsApp channel. Owner mail currently conveys booking/lead business events, not infrastructure errors (`src/db/schema.ts:27–44`; `src/lib/leads/create-lead.ts:174–181`; `src/lib/whatsapp/booking.ts:181–202`).

Reuse **Langfuse turn tracing**, not as a dead-letter queue: ADR-0001 traces every production Turn with masked contact fields (`docs/adr/0001-trace-every-production-turn.md:5–7`; vocabulary `GLOSSARY.md:23–34`). Traces start only once reply work is known; unknown phone/pre-turn failures and later delivery sweeps are not covered. Returned failed delivery outcomes do not throw into the turn trace (`src/lib/whatsapp/worker.ts:383–395,439–450`; `src/lib/tracing/turn-trace.ts:113–133`). Keep row-level operator logs in addition to traces. No tracing package change is needed for this decision.

Existing dashboard health is **email failures + maintenance cron**, not WhatsApp (`src/app/dashboard/overview/queries.ts:115–136`). `cron_runs` is written by email maintenance (`src/lib/email/maintenance.ts:79–106`), so rollout notes implying WhatsApp cron run rows overstate today's visibility. Do not repurpose these maintenance metrics as WhatsApp health without separate work.

Retaining dead rows is consistent with ADR-0002's audit/learning preference, but that ADR specifically concerns conversations/transcripts, not an unlimited queue-payload retention mandate (`docs/adr/0002-keep-all-conversation-data.md:5–15`). The checked-out maintenance code still purges transcripts, contradicting that accepted ADR (`src/lib/email/maintenance.ts:55–76,94`); flag separately, do not expand #68 into a retention rewrite. No domain ADR dictates retry limits or a terminal failure name (`docs/adr/0001-trace-every-production-turn.md:5–7`; `docs/adr/0002-keep-all-conversation-data.md:5–15`).

## 4. Decision 3 — claim ordering and indexes

| Option (all due rows only) | Tradeoff |
| --- | --- |
| A. `next_attempt_at, created_at, id` | Fair to oldest eligible retry; easy due-oriented index, but old poison backlog still wins over first executions. Does not meet fresh-first intent. |
| **B. `attempts, created_at, id` (recommended)** | Fresh first, then less-retried work, oldest deterministic ties. Simple Drizzle `.orderBy(...)`; retries can starve under sustained fresh load. Requires corrected counter semantics (§2). |
| C. Two lanes / reservation (e.g. 8 fresh + 2 retries; 20 fresh + 5 retries) | Guaranteed retry capacity, oldest due retries in their lane; more claim queries and unused-lane refill logic. Choose later if pilot demonstrates retry starvation. |

Keep `state IN ('pending','failed') AND next_attempt_at <= now()` and claim/update in the same short transaction; **order before `LIMIT`**, not in JavaScript after selecting an arbitrary batch. Add `id` because equal `created_at` values alone do not provide a unique order. PostgreSQL explicitly warns limited results are unpredictable without a unique order and identifies `SKIP LOCKED` as suitable for multiple consumers of queue-like tables ([SELECT][pg-select]). Skipped locked rows and concurrent runs mean this is preference among available rows, **not strict global FIFO**. Do not use a “lock whole subquery then sort” workaround: Postgres warns it locks many more rows ([SELECT locking caveat][pg-select-lock]).

**Migration recommendation:** add `dead` to both Drizzle enums in a new generated migration; keep old migrations untouched (`drizzle.config.ts:3–10`; `package.json:20–21`). Claim-order correctness needs **no index migration** initially: retain `(state,next_attempt_at)` to find candidates and sort the small due set. Those indexes do **not** satisfy `ORDER BY attempts,created_at,id` (`src/db/schema.ts:625,665`; [B-tree ordering][pg-order]).

If due backlog makes sorting costly, benchmark a partial B-tree on `(attempts,created_at,id) WHERE state IN ('pending','failed')` for **each table**, alongside the existing due index. It matches ordering and excludes terminal/sent rows, but cannot efficiently narrow a due-time range from its leading keys; future-due low-attempt rows may need scanning. Conversely `(next_attempt_at,attempts,created_at,id)` finds due rows but cannot produce attempts-first ordering. Adding `next_attempt_at` at the end of the order index does not remove that tradeoff ([multicolumn indexes][pg-multicolumn]; [index ordering][pg-order]; [partial indexes][pg-partial]). Use actual generated SQL and representative `EXPLAIN (ANALYZE, BUFFERS)` on a representative test database, rolling back any claim transaction; `ANALYZE` executes the query and `FOR UPDATE` locks rows, so this is not a read-only transaction. For a partial index, confirm the actual parameterized Drizzle predicate lets the planner prove the index predicate (generic parameterized plans may not; [partial indexes][pg-partial]). Do not prematurely replace the due indexes.

**Ordering limit:** a newer message in the same conversation can overtake an older failed job; `claimGenerating` serializes execution but does not implement per-conversation FIFO (`src/lib/whatsapp/worker.ts:359–369`; `src/lib/whatsapp/inbound.ts:181–200`). Meta also does not guarantee delivery order of multiple sends; strict sequence requires waiting for delivered status ([Meta service messages][meta-messages]). This issue fixes queue preference, not conversational causality/chunk delivery ordering. Raise a separate head-of-line policy if that guarantee is required.

## 5. Existing rows and rollout (proposal only — nothing executed)

1. **Stop the owning worker during coordinated cleanup**, not the shared database. Shared Supabase/Docker is a repo-wide invariant (`docs/local-development.md:70–84`). Preserve the root's existing unrelated work; this research does not apply any migration.
2. After enum/policy deployment, preview exact candidate IDs, payload phone ID, School mapping, error, state and attempts. Terminalize known permanent `pending|failed` rows (unknown-number, closed-window, unapproved-school, permanent provider codes) and rows already at/over the budget. Preserve errors/dedupe keys, clear claims; do not requeue `sent|delivered|read` wholesale. `school_id IS NULL` alone is not an orphan test: **all new jobs enqueue with no school ID** (`src/lib/whatsapp/jobs.ts:20–29`). Compare phone ID to actual School mapping (`src/lib/whatsapp/inbound.ts:31–37`).
3. Issue #68 reports failed `199…` test jobs with `unknown_phone_number`; **this pass did not query or mutate the live local DB** ([issue #68](https://github.com/fillthemat/fillthemat/issues/68)). The route integration suite creates `199…` phone IDs but deletes only the owner/auth user, leaving job rows; School deletion sets their school ID null (`src/app/api/webhooks/whatsapp/route.integration.test.ts:35–38,109–113`; `src/db/schema.ts:666–670`). For confirmed test artifacts, terminalization preserves evidence; optional deletion must use reviewed exact IDs/test provenance, never “delete every 199-prefix job.” Production mapping mistakes should remain inspectable.
4. Existing attempt counts are **failure counts**, so deployment cannot reconstruct accepted-send executions that failed asynchronously. For active `failed` deliveries with a `provider_id` and attempts zero, account for at least that known accepted send; flag others as legacy/unknown instead of claiming an exact history. An operator can deliberately rearm a reviewed row with a fresh explicit budget after checking window, booking usefulness and prior side effects. Reusing the original row/dedupe key prevents a replayed webhook creating a second job (`src/lib/whatsapp/jobs.ts:20–31`). ## Maintainer-only choices

1. **Who checks pilot terminal rows/logs, and how often?** If nobody owns manual review, option §3.2 needs an actual operator recipient/alert destination before rollout.
2. **Is five total executions + daily idle retry cadence acceptable?** Five is recommended; cadence remains the accepted Hobby tradeoff, not fixed by this issue.
3. **Can fresh traffic starve older retries / overtake old failed turns?** Recommended v1 accepts that preference; guaranteed progress/FIFO means option C or conversation head-of-line work.
4. **When are booking confirmations too stale to send, and should an undeliverable confirmation trigger School Owner follow-up?** Business policy, not Meta error classification.
5. **Should real inbound-window timestamp plumbing land with #68 or as a separate pre-pilot fix?** It is needed for faithful window enforcement under delayed execution (§2); generic template fallback remains a separate product decision.

## Maintainer decisions (2026-10-09)

1. **Nobody monitors terminal rows.** Option §3.1 (logs + manual table query) is therefore not a real control for the pilot. Terminal transitions still log once, but anything that needs a human must push a notification to a recipient who already reads email (see 4). Operator alerting for infrastructure/config failures (credentials, unknown-number spikes) has no owner; record it in `docs/known-gaps.md` as an accepted pilot gap rather than building an alert nobody reads.
2. **Five total executions, retried quickly right after failure.** Daily-only retry cadence is not the goal. Hobby cron cannot wake more than daily, and the timed-wake fallback (`pg_cron` → `pg_net`) needs Supabase Pro for pause-safety (`docs/decisions/whatsapp-cron-after.md:333,487–516`). Hobby-safe shape to evaluate in implementation: retry transient failures **inside the same `after()`/worker invocation** with short in-process delays (seconds, not 1/2/4/8 minutes), bounded well within the 300 s Hobby function budget (`docs/decisions/whatsapp-cron-after.md:240–246`); whatever budget remains after the invocation ends falls back to the daily sweeper. Document the minute-scale timed retry as deferred infra (Vercel Pro cron or Supabase `pg_cron`) and revisit before/after pilot.
3. **Separate lanes for fresh work and retries** (option §4.C). Each claim reserves capacity for retries (e.g. jobs 8 fresh + 2 retry, deliveries 20 + 5) and refills unused lane capacity from the other, so retries make reliable progress and never displace new inbound messages. Index needs per §4 still apply per lane.
4. **External sends to any channel get the same five-execution cap**, and when a booking confirmation (or other owner-relevant send) goes `dead`, the **School Owner is notified by email** via existing owner mail plumbing — rate-limited/batched, with its own capped retries so it cannot loop (§3 option 3). Prospects are never notified through the failed channel. Staleness cut-off for booking confirmations (e.g. booking start) is still an implementation detail; default to "do not send after the booked class has started".
5. **Inbound-window timestamp plumbing — split out** into its own pre-pilot issue linked to #68 (separate correctness bug: window computed from processing time, not the user's message time — §2).

### Grilling round 1 (2026-10-09) — refines the above

- **Owner email:** new owner email kind, sent once per booking, only when a prospect's WhatsApp **booking confirmation** goes `dead`. Ordinary assistant-reply failures only log.
- **Staleness:** a booking confirmation not sent before the booked class starts goes `dead` (reason: stale) with **no** owner email.
- **Fast retries:** after the run finishes its new work, it keeps claiming retries as they come due, at roughly 10 s / 20 s / 40 s / 80 s (five executions total), until nothing is near-due or a ~4-minute deadline (inside the 300 s Hobby budget). Applies to WhatsApp jobs and deliveries. Rows still failing are left for the daily sweeper, which uses the **same** five-execution budget (no reset).
- **Email channel in scope:** email deliveries get the same five-execution cap and `dead` state, as a separate ticket in the same spec. No notification when an email goes `dead`.
- **Lanes:** jobs 8 fresh + 2 retry, WhatsApp deliveries 20 + 5, email the same ratio scaled to its batch size; an empty lane's capacity refills from the other.
- **Docs:** no glossary terms (`dead`/lanes are mechanics, not domain language) and no ADR (reversible; this note is the record).
- **Tracking:** publish the spec as a new issue, then close #68 pointing to it.
- **Prospect fallback (round 2):** when an inbound job goes `dead` from *transient* exhaustion and the customer-service window is still open, send the prospect one fixed "trouble replying, please message again shortly" text. It is an ordinary capped delivery and never triggers a second fallback. No fallback for permanent failures (e.g. `unknown_phone_number`).
