# Current core/app code map

Resolution of [Map the current code: what is core, what is app, what is mixed?](https://github.com/fillthemat/fillthemat/issues/207), supporting [Map: extract a core agent platform beneath Fill the Mat](https://github.com/fillthemat/fillthemat/issues/204).

## Scope and reading key

- Snapshot: `origin/main` at `f54e1c4adce0ffdfcfd9e77c10e02eef851be771`, inspected 2026-10-12. All line references below are to that snapshot, **not** Poppy's branch. [Browse the source snapshot](https://github.com/fillthemat/fillthemat/tree/f54e1c4adce0ffdfcfd9e77c10e02eef851be771/src/lib).
- Primary evidence: the source and colocated tests, `CODING_STANDARDS.md`, and all four `docs/adr/` records. No running app, database inspection, migration, or source change was needed. This is a static coupling inventory, not a runtime correctness review or an extraction implementation.
- **Core** means domain-free agent driver/tool loop, channels, conversation state, delivery, handoff, and tracing/audit. Provider-specific WhatsApp or Langfuse adapters can still be core. **App** means Fill the Mat's schools, catalog, trials, bookings, leads, and dashboard. **Mixed** means both responsibilities live in the same file/interface, including a generic mechanism importing app policy.
- The decided driver seam supports **both hosted and bring-your-own agents**; injecting `LanguageModel` alone does not satisfy it. See [Hosted agent, bring-your-own agent, or both?](https://github.com/fillthemat/fillthemat/issues/208).
- Sizes are relative **untangling scope**, not estimates of full extraction: **S** = local parameter/import/fixture change or keep a wholly app file; **M** = coordinated caller/adapter/test change; **L** = transactional or persistent identity/lifecycle change across files. Core/app rows have S because there is no semantic split to perform. Schema sizes include migration implications, but no migration is proposed here.
- Every file in the requested directories is listed, including tests. In each table, `file:line` means the file named by that row, prefixed by its table directory. Ranges identify a responsibility or repeated use, not just a keyword. App rows show domain ownership, not accidental leaks; test fixture mentions are distinguished from behavioral coupling.

## Findings in brief

There is reusable core behavior, but **no existing domain-free core interface**. The easiest pieces are webhook parsing/signatures, Graph transport, chunking, dependency injection, and masking/export registration. The driver, channel orchestration, conversation store, durable delivery, and tenancy are mixed. Tools and booking/lead workflows should stay app-owned, rather than becoming renamed core concepts.

The strongest knot is **conversation identity/lifecycle plus app effects**: `schoolId` is the tenant everywhere, the store expires booking intents on close, and the worker commits messages, booking/lead effects, and delivery outboxes together. Moving folders would preserve that knot. The hardest part of making a school/trial/booking/lead-free glossary is expressing conversation ownership, Counterpart identity, and lifecycle effects without defining a generic "Booking Intent" or silently weakening transactional guarantees.

## Cleanest first seam

**Place the Agent Driver interface between channel Turn orchestration and agent execution**, at today's `streamedReply`/`completedReply` calls (`web-chat.ts:122`; `worker.ts:242`). Split the internal hosted implementation at `assistant.ts:48-74`, so the `ToolLoopAgent` adapter accepts assembled authored instructions, tool definitions, model configuration and execution limits rather than schools/catalogs. Fill the Mat supplies its instructions/context/tools and interprets results. A bring-your-own adapter supplies its own execution; it need not use `LanguageModel` or `ToolLoopAgent`.

Keep the public interface small: scoped Agent/conversation identity, accepted history/input, reply stream or completed output, completion/failure and provenance. SDK-native UI parts can remain an internal hosted/web adapter format initially; requiring external drivers to know Fill the Mat's inferred `AssistantUIMessage` or its four tool names would defeat the seam. Hosting config and external-driver credentials remain with their adapters.

**Do not put `bookingIntent`/`leadRequest` on the core result type.** A Fill the Mat result handler owns last-result conversion, booking-over-lead precedence, deterministic confirmation routing, consent and writes. Keep its message/effect/outbox work inside the current transaction: `worker.ts:268-355` is valuable atomicity, not disposable duplication. ADR-0003 and `CODING_STANDARDS.md:15-17` require that tools prepare and the platform writes. A small hash-input injection in `provenance.ts` is an easy enabling S change, not the platform interface by itself.

Why first: agent execution is already concentrated in one file, has both streaming and completed entry points, and both channels have clear call sites. It needs no table migration to begin. Prove it with two adapters (hosted and a domain-free fake external driver) and the same Turn tests. Then address conversation ownership/lifecycle, then delivery policy/association splits. This is a sequencing recommendation, not authorization to implement or a go/no-go verdict.

## Hardest glossary obstacle and adjacent coupling

Within the “core glossary writable without schools/trials/bookings/leads” criterion, **Operator–Agent–Counterpart ownership and conversation lifecycle** is hardest, not the vocabulary for tools. Today School serves simultaneously as tenant, prompt owner, channel endpoint owner, trace user and booking authority. A WhatsApp sender is identified per school; a web resume token cannot transfer even after conversation end. Closing expires a booking intent; a booking attaches a CRM contact. These are different roles with different invariants, not one safe global replacement of “School” with “Operator.”

App effects at the seam also need an honest definition: an optional opaque effect/correlation can cross a core interface, but core must not interpret trial availability, participant age, booking confirmation, lead consent or owner notification. Handoff must pause/reassign/allow replies on an existing conversation, not become a synonym for a Lead Request. No implemented human-handoff module exists in the requested main snapshot; Poppy's proposed protocol handoff is evidence to evaluate, not a landed general operator workflow.
