# Vercel-native core: commodity plumbing and the reliability boundary

Research for [#216](https://github.com/fillthemat/fillthemat/issues/216), checked **12 October 2026**. Builds on [build vs adopt (#205)](https://github.com/fillthemat/fillthemat/blob/research/build-vs-adopt/docs/research/core-build-vs-adopt.md) and [the current code map (#207)](https://github.com/fillthemat/fillthemat/blob/research/core-code-map/docs/research/core-code-map.md), rather than repeating their framework comparison. Source snapshot: `origin/main` at `f54e1c4adce0ffdfcfd9e77c10e02eef851be771`. Planning only: no implementation, dependency changes, production inspection, or change to map #204 or Poppy PR #200. [S1, S2]

## Answer

**Keep AI SDK for the hosted driver; evaluate Workflow as the durable execution backend; adopt Chat SDK selectively for channel transport.** Vercel can absorb webhook normalization, channel rendering, model/tool loops, stream protocol/replay, step checkpointing, retry scheduling, waits, and worker dispatch. It does **not** absorb our canonical acceptance/commit contract, outbound intent, semantic retry decisions, uncertain external-send outcomes, conversation ownership/takeover fencing, or retained audit. Workflow already uses Vercel Queues: do not add a second queue layer merely to make Workflow durable. Use Queues directly only when low-level ingestion, fan-out, or dispatch control justifies it. [S3–S11]

The remaining core is a **thin conversation control plane backed by our database**, not a replacement workflow engine. This is consistent with #205's conditional rung-1 recommendation, not new evidence that a generic platform must be built. Keep the hosted/BYO driver seam: Workflow can call an external agent inside steps without converting that agent's private loop/tools into `WorkflowAgent`. [S1, S6, S8]

Three source-level traps sharpen the recommendation:

1. Our WhatsApp route intends enqueue-before-ack but catches enqueue/status errors and still returns 200. **The current implementation is not lossless on database failure.** Swapping transport does not fix this contract. [S2a]
2. Chat SDK's default overlap strategy drops messages; its queues are bounded, expiring, and coalescing. Its pinned WhatsApp webhook dispatches handlers without awaiting durable acceptance and does not process delivery statuses. **Neither the example webhook nor `concurrency: "queue"` replaces our durable inbox/outbox.** [S3, S4, S12]
3. `chat/workflow.requestApproval` finalizes by editing the original message. The pinned WhatsApp adapter throws on edits, so **the helper is not a drop-in replacement for WhatsApp booking confirmation**, even though cards/buttons and durable waits are available separately. [S5, S12]

## Chat SDK: transport/state, not acceptance or takeover

### Web adapter

The adapter speaks AI SDK's UI stream protocol; `getUser(request)` is **our security boundary** (null → 401). It uses only the latest user message, strips tool parts, and uses configured persisted history rather than trusting browser-supplied prior turns. Default thread IDs include user + conversation, but neither is automatically our school's scoped resume-token authorization. Preserve that check rather than accepting an arbitrary client chat ID. [S3]

The pinned adapter passes `request.signal` into request-local context; posting outside an active web request throws. Its streaming iterator honors the signal, and its `handleWebhook` returns an ordinary SSE response without setting up a resumable-stream backend. A wrapper's `resume` option passes through to AI SDK; **it does not create a GET replay endpoint or persistent generation by itself**. Moving `thread.post()` into a detached Workflow is therefore not a transparent swap for web: use Workflow's durable stream transport at that boundary, or explicitly bridge the protocols. Main currently drains a copy of the SSE stream so generation can finish after a browser disconnect; that remains process/function-bound, not crash-durable. [S3, S7, S12, S2e]

### WhatsApp adapter

Commodity coverage is substantial: signature verification, actions/cards, text splitting, templates, media, read/typing, phone/BSUID identity aliases and rotation. Its configuration uses `WHATSAPP_ACCESS_TOKEN`, unlike our current `WHATSAPP_SYSTEM_USER_TOKEN`; thread identity contains phone-number endpoint + user. Keep explicit credential configuration and tenant routing—do not substitute an environment variable/default singleton for multi-tenant authorization. WhatsApp stream output is buffered then sent, not edited incrementally. [S4, S12, S2a]

At `4.41.1`, `handleWebhook` reads/verifies the request, loops over `value.messages`, invokes message/action processing, and returns 200; errors encountered in its per-message handling are logged. The published artifact has **no `statuses` handling**. `waitUntil` keeps a promise attached to an invocation; it is not an inbox commit or durable retry guarantee. Chat's error-propagation option exposes handler failures via collected promises but does not itself change the response, and SDK dedupe can suppress a redelivered failed event. Consequently, persist/verify acceptance **before** delegating asynchronous application handling, and retain a status-event ingestion path. An enqueue handler after SDK dispatch is not, by itself, proof of lossless webhook admission. [S12, S15]

Outgoing `postMessage` may split one reply into multiple provider messages. Our current outbox records each text chunk separately. A migration must preserve per-chunk intent/outcome/receipt identities, not treat one returned SDK message ID as evidence that the whole logical reply delivered. Retain the current sender where the adapter cannot expose the evidence required by our contract. [S4, S12, S2a]

### State, history and concurrency

Postgres state stores subscriptions, locks, cache, lists and queues. It auto-creates schema by default; any adoption should use migration-owned provisioning (`autoCreateSchema:false`) and scoped credentials, not runtime DDL. It uses a `pg.Pool`; sharing a database does not mean its operations join our existing Drizzle transaction. Redis offers efficient atomic leases/queues, but adds infrastructure. Neither backend turns SDK caches into our transactional conversation ledger. [S10]

Chat history is useful for model context: user-scope identity can link platforms; count eviction can be disabled and retention omitted. However, user history requires deliberate assistant appends; resolver errors dispatch without user-history persistence. Thread caches have separately configured limits/TTL. ADR-0002 must be preserved in our canonical store, not assumed from the word “history.” Tenant-scope any cross-channel resolver; email/phone coincidence is not permission to join customers across schools. [S10, S2c]

| Concurrency mode | Actual behavior | Suitability here |
| --- | --- | --- |
| `drop` (default) | Busy lock → discard message + `LockError`; no retry | Not our accepted-message contract. |
| `queue` | After current handler, dispatch latest queued message; intermediate entries in `context.skipped` | A batching mechanism only; persist/process every accepted event or explicitly record coalescing. |
| `burst` | Debounce idle burst, then latest + `skipped`, draining arrivals during work | Useful UX after canonical acceptance; earlier messages cannot silently disappear. |
| `debounce` | Replace pending message; earlier messages dropped | Only for explicitly replaceable inputs, not generic customer intake. |
| `concurrent` | No locking | Only safe when our control plane serializes/fences mutations or the handler is stateless. |

Default queue capacity is **10**, eviction **drop-oldest**, entry TTL **90 seconds**; lock renewal has a **10-minute** maximum lifetime. WhatsApp defaults to channel-scoped locks. These are reasonable SDK safeguards but not a lossless, indefinitely recoverable ordered inbox, and increasing them does not solve crash recovery/acknowledgment. If our inbox owns serialization, avoid adding conflicting SDK admission locks; using `concurrent` to dispatch persisted IDs is an option to test, not a recommendation to run unfenced agent turns concurrently. [S3]

### `chat/workflow` approvals

`requestApproval` supplies a Workflow webhook wait, Approve/Deny card, timeout, identity of decider, and optional `approvers`; setup requires Workflow and a registered Chat singleton for revived threads. Default visibility-based approval is too permissive for consequential operations—restrict approvers and validate scope/intent again when committing. These primitives reduce approval polling/dispatch work, **not** operator assignment, conversation takeover, or booking validity enforcement. [S5]

The published helper awaits `finalizeApprovalCard`, which calls `thread.adapter.editMessage`, **before returning the decision**, including timeout. WhatsApp's adapter throws for edits, so even receipt of an approval does not establish successful completion of this helper there. Web posting is request-local. Evaluate supported channels individually; for WhatsApp, compose durable hooks + native buttons + follow-up outcome messages, retain app intent expiry/confirmation, and audit decisions in our database. The generic helper's edited card is a UX audit trail, not our retained authoritative audit. [S12]

## Workflow, WorkflowAgent and streams

### What becomes durable

Workflow persists completed steps and replays orchestration; sleeps/hooks remove the need to keep an invocation alive waiting for a retry or approval. `WorkflowAgent` is the durable hosted AI SDK loop, with serializable tool schemas/context and model/tool checkpoints. **Tools without `"use step"` remain ordinary in-memory functions**. Current `stream()` emits raw `ModelCallStreamPart`; convert at the response boundary with `createModelCallToUIChunkTransform`. Retain the app's “tools prepare, platform writes” split: tool durability does not authorize moving booking/lead writes into the model loop. [S6, S8, S2e]

Start with a bounded **one-turn run** whose app commit remains one database transaction and whose sender receives committed delivery IDs. Do not split message persistence, booking/lead writes, and outbox insertion into independent workflow steps: checkpoint persistence is not a transaction across those effects. Stable domain action IDs must dedupe a commit whose DB success was followed by loss of the step-result acknowledgment. [S2a, S8]

`start()` + a DB update is not atomic. Deterministic hook tokens coordinate **active** duplicate runs only after registration; check `hook.getConflict()` before duplicate-sensitive steps. Lookup then start remains racy, and a completed run's token becomes reusable unless experimental minimum retention is configured. Thus retain domain inbox/action uniqueness and a recoverable dispatch/start mapping; step IDs dedupe one step's retries, not a replacement run or unrelated invocation. Do not rely on experimental forced-hook takeover to revoke already-running sends. [S8]

Retries require an explicit adapter to our policy. Workflow defaults to **3 retries = 4 total attempts** on arbitrary step errors (`maxRetries` counts retries); current policy permits **5 started executions total**, including crashes. `FatalError` skips retry, `RetryableError.retryAfter` schedules delay, and `maxRetries` can cap execution. Do not naively wrap an already retrying worker/sender in another retrying step and multiply attempts. Queue `deliveryCount`, workflow attempts, AI provider retries and semantic send executions are distinct counts. Preserve a persisted business attempt budget and terminal effects even if scheduling moves to Vercel. [S8, S2a]

Current WorkflowAgent documentation distinguishes `needsApproval` on its tools from core v7 `toolApproval` on `ToolLoopAgent`/`generateText`/`streamText`. Signed approval support is experimental and binds the issued input; it is not our tenant authorization or booking revalidation. Durable context must be serializable; do not persist `School` rows indiscriminately, DB clients, live credentials or runtime SDK objects. Configure an explicit `stopWhen` matching our existing `MAX_AGENT_STEPS`: streaming WorkflowAgent has no default step ceiling, while current docs describe a 20-step default for `generate()`. Re-check `generate()`/`stream()` differences with the installed evaluation package, not assumed API parity. [S6, S16]

### Two different resume choices

| Choice | Solves | Does not solve | Recommendation |
| --- | --- | --- | --- |
| AI SDK `resume` + `resumable-stream` + Redis | Reconnect/replay UI chunks while a producer is running; reload/visibility recovery | Restart a dead model/tool process; acceptance; authoritative transcript; cancellation semantics | Small optional UX improvement if Workflow is deferred; adds Redis and active-stream lifecycle work. |
| Workflow stream + `WorkflowChatTransport` | Durable output replay plus durable producer checkpoints; reconnect when no finish event arrives | Tenant access to run IDs; final transcript commit; exactly-once side effects; takeover | Prefer for the durable hosted-driver spike; avoid implementing two replay backends at once. |

Workflow transport needs an `x-workflow-run-id` header and `{api}/{runId}/stream` GET route. For raw model parts, **UI chunk cursor and raw stored chunk index differ**: replay raw from index 0 and apply non-negative `uiStartIndex` through the transform. Model retries emit reset-step events so partial failed-step output can be removed. Validate replay/duplicate text, error and terminal completion behavior with the actual UI, rather than merely checking that SSE reconnects. [S6, S7, S11]

Both choices require a persisted authorized link between tenant/conversation/accepted turn and active stream/run. A run ID is not an authorization credential. Persist final `UIMessage` transcript independently; WorkflowAgent's returned `ModelMessage[]` is not a complete substitute for renderable UI history. Navigation disconnect is distinct from explicit stop: resumable AI SDK `stop()` disconnects the reader; an authenticated endpoint must stop the producer and clear only the matching active turn, without replacing newer server-written content with a stale client snapshot. [S6, S7]

Workflow run cancellation stops orchestration at the next suspension, disposes hooks and closes streams, **but in-flight steps continue**. Cooperative AbortSignal can cancel operations that honor it; it cannot undo a provider send. This is why takeover needs an application ownership fence, not just `run.cancel()`. Stream reader invocations also have function-duration/cancellation considerations; the current Node-specific `supportsCancellation` guidance must not be assumed to cover this repo's Bun deployment without testing. [S11, S14]

## Direct Vercel Queues: useful dispatch, bounded guarantee

Queues gives durable replicated acceptance, at-least-once delivery, visibility leases, retry callbacks, fan-out and delayed dispatch. It can replace raw job polling/requeue machinery or wake inbox/outbox processing. It does not require `WorkflowAgent`, and it is not necessary as an extra topic around every Workflow run. [S9]

Explicit design constraints from the primary docs:

- **No FIFO**, even max concurrency 1; retries have lower priority than fresh messages. Preserve per-conversation sequence/ordering policy ourselves. Our current fresh/retry lanes reserve retry capacity, so queue priority is not automatically equivalent fairness. [S9, S2a]
- Retention **60 seconds–7 days, default 24 hours**. Accepted work can expire before successful processing; retain canonical recoverable work and alert/reconcile before expiry. Publish dedupe window is `min(retention, 24 hours)` and filtering occurs after publish returns; it cannot replace permanent domain dedupe. [S9]
- Visibility timeout defaults **60 seconds**, configurable to **3,600 seconds**, with lease extension. Long handlers must not accidentally create concurrent executions when a lease expires. A lease is not a downstream ownership fence. [S9]
- **No built-in DLQ**. Retry callback acknowledgment or `maxDeliveries` stops redelivery; persist terminal/poisoned evidence and recovery intent before dropping/acknowledging it. Default max deliveries is unlimited. [S9]
- Push topics are deployment-partitioned and callbacks remain on the publishing deployment. A rollback/promotion does not stop older consumers; deleting a deployment stops invocations but leaves pending messages to expire. Coordinate draining, dispatch versions, and recovery from canonical records rather than assuming rollback transfers the backlog. [S9]
- Managed acceptance does not atomically commit our Postgres business writes. Publish committed opaque IDs through a durable DB dispatch record/reconciler; avoid acknowledging an inbound webhook based on a fire-and-forget `after()` publish. [S8, S9; application recommendation]

## Reliability responsibility matrix

These are proposed acceptance requirements, not claims that main already implements them. “Ours” can mean a small policy adapter/transaction around SDK primitives, not bespoke infrastructure.

| Requirement | Vendor mechanism | Our irreducible responsibility / current gap |
| --- | --- | --- |
| **Lossless inbox** | Durable queue publish or workflow start; Chat normalization/dedupe | Store tenant-scoped accepted input/action identity before success acknowledgment; dedupe across restarts and completed runs; record sequencing/coalescing, retry/dead state and dispatch recovery. Main's route catches persistence failures and acks anyway; web busy/duplicate responses are admission decisions, not accepted durable turns. [S2a, S3, S8, S9, S12] |
| **Outbound intent** | Durable step/queue consumer executes an intent | Commit reply/app effect/outbound payload together; send only afterward; retain stable delivery IDs and separate attempts/provider IDs/chunks; recover dispatch gaps. Main's assistant-turn transaction is valuable and must survive adoption. [S2a, S8] |
| **Retry classification** | Typed adapter errors; Fatal/Retryable errors; queue retry handler | Translate provider codes/window/deadlines and internal failures into retry/permanent/stale/unknown; bounded executions, due times, exhausted fallback and operator evidence. Framework defaults do not know business validity or our budget. [S2a, S4, S8, S9] |
| **Unknown outcomes** | Completed-step replay avoids repeating completed recorded work; stable step IDs help idempotent APIs | A successful external send with lost response/result write can still be repeated. Record “unknown/needs reconciliation,” inspect receipts where possible, and explicitly choose duplicate-vs-loss risk when provider dedupe is unavailable. Current `providerIdempotencyKey` is DB uniqueness and is **not transmitted** by `client.ts` as provider dedupe; network/malformed responses currently become bounded retries, not honest unknown resolution. [S2a, S8] |
| **Takeover fencing** | Chat leases; Workflow hooks and cancellation | Persist authorized owner/epoch; carry it through turn, commit and outbound intent; re-check/fence acceptance of stale driver output and sender eligibility when takeover/reclaim happens. Main's generation release compares timestamp, and queue finalizers compare owner/time/attempt, but transcript/app commits do not carry a general conversation ownership epoch. No general operator takeover is implemented in these main modules. [S2a, S2e, S11] |
| **Authoritative audit** | Workflow event logs/dashboards; Chat history/cards; OTel/Langfuse | Retain accepted events, driver/config provenance, action/approval/ownership transitions, frozen outbound intents, attempt results, receipts and explicit unknowns under our retention/deletion policy. Link vendor run/trace IDs; export failure must not erase authority. Main's provenance is primarily in best-effort traces, not complete retained audit rows. [S2c, S2d, S9, S10, S17] |

**External-send fence limit:** a database epoch check just before an HTTP send is not atomic with the provider. An in-flight send may already be accepted when takeover commits. Define a send-reservation/ownership protocol and an honest “already dispatched/unknown” boundary; do not promise retroactive suppression or exactly-once delivery from cancel/locks alone. Queue finalizer fencing prevents stale DB state updates, not provider effects already issued. [S8, S11; derived application requirement]

Keep OTel/Langfuse. AI SDK v7 telemetry is already registered here; moving to Workflow adds cross-step correlation work rather than eliminating `turn-trace.ts`. Preserve ADR-0001's one production trace per turn and masking; Workflow metadata/inputs have their own privacy surfaces. Keep canonical provenance/audit in the transaction, using trace/session/run IDs as supporting links. Trace dashboards are useful observability, not a replacement for our retained ledger or BYO visibility limits. [S2c, S2d, S6, S17]

## Adoption order that leaves Poppy alone

This is a recommended sequence for separately authorized follow-up work, **not** a migration started by this ticket.

1. **Preserve the existing baseline and identify the contract.** Keep AI SDK's hosted loop, database transcript/outboxes and Langfuse. Record the enqueue-failure acknowledgment gap, uncertain-send policy and required takeover/audit behavior as acceptance cases. Do not globally change channel unions, conversation/schema ownership, booking/lead writes, issuer identities, or extracted glossary while Poppy is in flight. [S1, S2, S18]
2. **Finish/re-map Poppy before touching its shared seam.** PR #200 is OPEN at observed head `a96cd0b110e1ef89a380017901db6f6bce4d8117`; it changes `ai/assistant.ts`, conversation store, channel, tracing, schema and booking/lead/email/security code, and adds Poppy-specific conversation/session/operation paths. It is not a Chat SDK WhatsApp/web replacement. Preserve permanent school-scoped issuer identity and #187's independent interop gate; do not block its landing on an orchestration choice. [S18, S2c]
3. **After re-mapping, prove the small driver/app-result seam from #207.** Keep hosted AI SDK as implementation one and use a domain-free fake external driver as implementation two. Keep last booking/contact result interpretation and the current atomic app commit outside the generic interface. No new workflow/transport dependency is needed for that test. [S1, S2e]
4. **Evaluate Workflow on a new isolated turn path, not a big-bang worker replacement.** Use the pinned Workflow/AI SDK pair; make execution/commit/sender boundaries explicit, with serialized IDs and stable domain actions. Prove restart, step-result-loss, duplicate start, callback race, and old-owner completion. Keep existing jobs/outboxes as the recovery authority until reconciliation is proven. Check deployed Next/Bun/compiler/proxy behavior separately. [S6, S8, S14]
5. **For web durability, use Workflow streams/transport once the driver spike passes.** Keep canonical UI history and authorization. If only reconnect UX is urgent and Workflow is deferred, the Redis replay alternative is smaller, but deliberately adds no producer-crash durability. Choose one backend, not both. [S6, S7, S11]
6. **Trial Chat SDK channel by channel.** Prefer a new channel/path first. Adopt WhatsApp formatting/normalization where it reduces code, but retain durable admission, statuses, per-chunk delivery evidence and app confirmation semantics; do not replace the current route with the quickstart. Use state-pg only if SDK state/history actually helps, with migration-owned schema. Re-evaluate web adapter request-bound behavior before sharing Workflow handlers. [S3–S5, S10, S12]
7. **Use direct Queues only for a demonstrated lower-level need.** If it wins for dispatch/fan-out, retire equivalent polling/claim timers after expiry/DLQ/deployment/retry-budget tests, not canonical inbox/outbox records. Do not simultaneously maintain nested SDK, DB-worker, queue and workflow retry loops for the same send. [S8, S9]

### Exit tests before deleting existing machinery

- Burst beyond 10 messages and 90 seconds, overlap, webhook duplicate after a completed run: every accepted input is retained, with explicit processing/coalescing outcome.
- DB unavailable during webhook acceptance: no false success; commit succeeds but publish/start fails: reconciler resumes from retained intent.
- Crash after model completion, after atomic app commit, after provider acceptance but before receipt/result persistence: no duplicated booking/lead, and no fabricated “not sent” certainty.
- Status-only callback, early callback before send-result save, stale callback from prior provider attempt, multi-chunk partial send: receipt correlation/ordering and recovery evidence survive.
- Takeover while streaming, waiting for approval, or sending; old workflow resumes after cancellation/rollback: stale application commits/output are fenced, with the in-flight-send exception recorded honestly.
- Browser reload/disconnect/timeout/stop plus failed-model-step replay: no duplicated UI content, leaked run access, cancellation of a newer turn, or lost final transcript.
- Retry exhaustion/window expiry/poisoned input: persisted terminal outcome and existing app notification behavior; attempts do not multiply across runtime layers.
- Trace export failure and vendor retention expiry: reconstruct retained input/action/ownership/delivery history and provenance without Langfuse or Workflow logs; preserve Poppy auth/interop and booking/contact contracts.

These are experiments, not results of this static research. A small compositional solution that passes them supports #205's thin control-plane option; SDK feature lists alone do not settle #204's build/adopt gate. [S1]
